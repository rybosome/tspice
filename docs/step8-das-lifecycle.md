# DAS creation, metadata and buffered writes

C04 exposes nine DAS routines in `FileIoApi`. Every scientific operation calls its matching CSPICE C entry point. Handles are backend-owned opaque claims and never expose a native file number. Metadata accepts existing read handles and DAS-backed DLA/DSK handles. A borrowed handle from another backend or an expired or wrong-kind token fails before dispatch. Native calls use the process-wide CSPICE lock. [Typed contract](../packages/backend-contract/src/domains/file-io.ts) [DAS required reading](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/das.html)

| Operation | Observable behavior                                                                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dasonw`  | Create a named DAS writer with case-sensitive four-byte type and 60-byte internal name. Reserve ncomr fixed 1024-byte records for comments.                |
| `dasops`  | Open an actual temporary DAS and return an owned writer claim. Its external name may be empty and its internal name is DAS SCRATCH FILE.                   |
| `dasopw`  | Open an existing DAS for exclusive write. Toolkit open conflicts and file absence are observed independently.                                              |
| `dashfn`  | Return the actual file name with caller namlen including NUL; the 255-byte toolkit field and unnamed scratch behavior are preserved.                       |
| `dashfs`  | Read four reserved/comment counters, the first free record and three ordered triples of logical addresses, directory record numbers and word locations.    |
| `daslla`  | Return the last logical character, double and integer addresses. All three values are observed independently.                                              |
| `dasllc`  | Release just one claim without flushing or segregating. Dirty data and process buffers require explicit caller handling.                                   |
| `dasrfr`  | Read the on-disk fixed header, including its eight-byte identification word, 60-byte internal name and all four counts. Output capacities are independent. |
| `daswbr`  | Flush updated buffered data records of a live writer. A reader signals the toolkit access diagnostic; the writer stays open.                               |

## File and handle lifetimes

DASONW creates a new file; DASOPW requires an existing native-format DAS. Node accepts host paths and resolves staged input aliases. WASM writes under its virtual kernel directory. An explicit `VirtualOutput` is readable after close through `kit.readVirtualOutput`; DASOPW accepts such an object only for a path already created by DASONW on that backend. Reopening its physical name also gates readback while the writer is live. Failed opens never publish a token. If registering a newly opened file fails, the adapter closes its native claim. A physical file created before registration failure may remain and can be reopened. Separate read calls produce separate tokens even when the toolkit shares their native handle. Closing one preserves the other's read claim. [Node lifecycle and rollback tests](../packages/backend-node/test/das-lifecycle-domain.test.ts) [WASM allocation and namespace tests](../packages/backend-wasm/test/das-lifecycle-allocations.test.ts)

The common close operation DASCLS flushes and finalizes an ordinary writer. DASWBR followed by DASLLC writes buffered data without segregation. DASLLC alone does neither. In the pinned toolkit, low-closing a dirty DLA can discard its three buffered integer logical addresses. Unflushed records may also remain in process-global DAS buffers and cause a later operation on a different file to signal NOSUCHHANDLE. A caller retaining data or reusing the SPICE process must flush before low-level close. A scratch file uses the toolkit's scratch unit and is removed when closed; its name is runtime-dependent. On the tested unnamed temporary-file runtimes DASHFN returns the empty string. N0067 DASOPS uses a static file identifier when writing a scratch header. Following a named open with type ABCD it can return `DAS/ABCD` together with the independent internal name `DAS SCRATCH FILE`. No fixed `DAS/SCR` is assumed. [NAIF DASLLC](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/cspice/dasllc_c.html) [NAIF DASOPS](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/cspice/dasops_c.html)

## Fixed storage and names

N0067 DASONW calculates the initial first free record as `ncomr + 3` and opens its first directory record at `ncomr + 2`. Its f2c DUE implementation seeks with a signed C `long` and 1024-byte records. The wrapper rejects values outside either the record index or file-position range before opening a file. In wasm32 the largest permitted count under this bound is 2,097,149. Actual allocation is subject to runtime resources. Negative representable counts are passed through for CSPICE's INVALIDCOUNT diagnostic. The physical pathname must fit the toolkit's 255-byte file-name field. DAS file record strings default to 9 and 61 allocated bytes, including NUL. DASHFN defaults to 256 bytes. Smaller lengths reach CSPICE and lengths above the source maximum use only its full physical field. Both adapters preserve valid UTF-8 and reject a truncated multibyte sequence that cannot form a JS string. Every text buffer is initialized before the C wrappers' unconditional Fortran string conversion, including the INQUIRE path that supplies no name for an unnamed unit. [Shared C adapter](../packages/backend-shim-c/src/domains/file_io.c) [Independent typed string oracle](../packages/py-parity-checking/sidecars/spiceypy/src/py_parity_sidecar/das_file_oracle.py)

Complete summary arrays retain the native character, double, integer ordering. Directory positions and logical addresses remain one-based where used; zeroes and other unused-address sentinels are preserved as returned. External file names are scoped to their actual runtime. Registered DASHFN comparisons remove the known backend-specific staging root while retaining the returned relative name; truncation is also compared by filename capacity and direct physical-name tests exercise the raw path. Tests use repository-authored scratch files, the existing authored EK/DSK and the existing Apophis DSK fixture. [Fixture provenance](../packages/py-parity-checking/fixtures/README.md)
