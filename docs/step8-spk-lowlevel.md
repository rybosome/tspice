# SPK segment loading, evaluation and physical subsets

The E03 raw methods operate on actual N0067 file registrations, descriptors and segment data. A path can name a physical file on Node, an already staged kernel, or a closed virtual output on either backend.

| Call                                                    | Observable result                                                                                                                                        |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spklef(file)`                                          | Client-owned SPK registration. Loading again promotes the file to highest priority and returns the same local token for that live registration.          |
| `spkuef(token)`                                         | Removes the registration from the SPK subsystem. A single unload removes a repeated load.                                                                |
| `spkpvn(source, descriptor, et)`                        | `{ref, state, center}` with integer frame and center IDs and six components in the segment's native frame, km and km/s. ET is TDB seconds after J2000.   |
| `spksub(source, descriptor, ident, begin, end, writer)` | Appends an independently readable subset to a distinct open SPK writer. The subset includes both supplied TDB endpoints, including a one-epoch interval. |

## File ownership and search state

SPKLEF updates SPKBSR independently of KEEPER. Loading two overlapping files, promoting the older one and unloading it changes the actual winner returned by SPKSFS. KEEPER clear permits a direct-only file to survive. When KEEPER removes a file it also registered, the corresponding former SPK generation expires even when another DAF read link retains the physical handle. A later direct unload of that expired claim delegates to the toolkit's documented absent-file behavior and leaves any newer registration available. Client disposal releases outstanding direct claims before tearing down staging. All of these operations share the native CSPICE mutex or the owning WASM instance. Stateful search/evaluation operations bypass the facade's default result cache.

A source may be a local explicit SPK load, a local readable DAF, or a physical number previously returned by that client's SPKSFS. Source registration tokens survive a higher-priority file being loaded. Supplying another client's opaque token fails lookup. Physical numbers have the identity precision of the existing SPKSFS API; a new successful search for a reused number refreshes that client's observation. Node staging resolves a staged KEEPER path and the corresponding direct load to the same underlying file. The initial registered comparison caught a separate temporary copy in the harness, which would have changed the toolkit's de-duplication behavior. Both sides now observe the same physical identity within their separate runtime.

## Exact descriptors and file access

The source descriptor is an actual five-word SPKSFS tuple or 40 native-order DAFGS bytes. Packed integer pairs can have noncanonical NaN bits. The tuple retains its original bytes through worker transport. Before interpretation, the shim matches every byte against the source SPK's physical summary records using the C01/C02 record APIs, then checks address extents and finite ordered descriptor epochs. This read preserves the current DAF search selection. Authentic descriptors from different files are interchangeable only when all 40 bytes actually match a real summary in the selected file. Callers must supply a valid SPK file. The write target is a separate owned SPK output from SPKOPN or SPKOPA. The shim also checks its underlying DAF write access, ID word and summary dimensions.

SPKPVN's record readers have different extrapolation domains. Type 8 reports the actual SPICE(TIMEOUTOFBOUNDS) status outside coverage. Types 2 and 3 select a coefficient record using a signed conversion before applying an upper clamp. Type 20 clamps both ways. The shim checks the actual file trailer, count, record width, storage extent and representable conversion before dispatch, retaining ordinary out-of-coverage coefficient evaluation. Types 1 and 21 can select an epoch beyond descriptor coverage when the physical last record still covers it; the upper check uses that physical epoch directory. Type 10 selects the nearest one or two element sets. The shim reads those same packets through SPKR10, preserves ordinary extrapolation and bounds the translated calendar day of each element epoch to ±1.6×10¹⁴ seconds. For an offset reaching one million 720-minute steps it uses ZZINIL's corrected mean motion to identify a resonant orbit; traced SGP4 initialization preserves errors preceding that work limit. Ordinary evaluations always call SPKPVN_C. Validation checks guard supported inputs before entering a reader with unrepresentable addresses or an impractical resonant loop. Focused tests use safe calls to the independent library.

## Independent scientific observations

Twenty-seven registered workflows contain 222 steps and 116 calls to the four new methods. Eight end in a genuine toolkit error. In the order above, the methods account for 36, 28, 35 and 17 calls. Nonexistent files, an empty valid SPK, no remaining loaded files, out-of-range type-8 epochs, reversed or out-of-range subsets and an empty identifier exercise distinct outcomes. Error workflows seed their output with a valid segment so the normal SPKCLS finalizer can close it. Physical files and virtual outputs are created independently on each side. Locked SpiceyPy 6.0.3 calls all four public CSPICE functions directly. Full states use the existing componentwise 1e−12 absolute or relative comparator. Identifiers, addresses, frames, centers, interval boundaries, found flags and diagnostics have discrete checks.
